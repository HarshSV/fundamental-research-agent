## Ground rules for this work

1. **One ratio at a time.** The user will say which Sr No to fix next. Don't jump ahead to other flagged rows, don't batch multiple fixes into one change — but if fixing one Sr No's root cause also happens to fix a *different*, not-yet-asked-about Sr No (e.g. Sr 4 DSO was automatically fixed by Sr 3's fix, since DSO is a pure derivation of Receivables Turnover), say so explicitly rather than silently claiming it's separately verified.
2. **Never assume the code's internal `ratio_no` matches QA's "Sr No" column.** They frequently don't (e.g. QA's Sr 21 ROE is internally `ratio_no=18`; Sr 22 ROCE is internally `ratio_no=19`). Before touching Supabase, always `grep "try_db_ratio(sym," tools/nse_xbrl.py` near the relevant `fetch_*` function to find the REAL internal ratio_no — never guess.
3. **Verify against the real source, not just the code.** For each fix: find the actual Annual Report PDF text (via `tools/bse_scraper._sess()` + `fitz`) for the flagged company and confirm the bug reproduces, then confirm the fix against that same real text — don't just trust the code logic in isolation. When QA gives concrete numbers (e.g. "Non-current Lease Liabilities: ₹1,104 cr"), cross-check the PDF directly rather than trusting either QA's claim or the code's output blindly.
4. **"No bug found" needs real diligence, not a single check.** If you check one function call and it looks right, that is NOT enough to tell QA "this works" — QA is a real, human-verified signal. Check THREE layers before concluding something is fine: (a) live computation bypassing all caches, (b) the Supabase DB row `try_db_ratio()` actually serves, (c) the frontend component rendering that data. Several "no bug found" verdicts this session were wrong on the first pass because only layer (a) was checked.
5. **Push after every change.** As soon as a fix is verified working end-to-end, commit and push to `origin/main` immediately (explicit standing instruction from the user — do this without being asked each time). Don't batch multiple fixes into one commit. Write commit messages that explain the root cause and what was verified, not just "fix X".
6. **Check ALL cache layers before declaring something fixed or stuck**, in this order:
   - The shared PDF-extraction cache (`cache/bse/ar_extract_v3_<SYMBOL>_<YEAR>_<C|S>.json`)
   - The per-ratio file cache (`cache/nse_xbrl/<prefix>_<SYMBOL>_<to_date>.json` — prefix varies per ratio, check the actual `ckey = f"..."` line)
   - The Supabase `ratio_values` table (checked via `try_db_ratio` BEFORE any live computation runs, for `to_date=None`/"latest" queries only) — this can hold a value that was correct WHEN COMPUTED but is now stale because the code has since changed. `try_db_ratio`'s freshness guard (`tools/db_ratio_reader.py`) only catches "a newer fiscal year is now available" — it does NOT catch "same year, but the extraction logic that computed this row has since changed/been fixed". Any methodology or bug fix needs its OWN manual cache-bust.
   A fix can look "stuck" or "still broken" purely because of stale cache at any of these three layers, not because the code is wrong — verify each explicitly, in order, before concluding anything.
7. **Before any bulk Supabase delete** (clearing a `ratio_no` across all symbols), explicitly ask the user for confirmation with the exact row count and which ratio_no(s) — don't proceed on a general "fix everything" instruction from earlier in the conversation; each bulk delete needs its own explicit yes. This session established a repeatable pattern for this — see `tools/_refix_tcl_cash_ratios.py` (a scoped re-derivation script targeting only specific corrupted ratio_nos, faster than a full 2,400-company re-run).
8. **Be extremely careful with any guard/safety-check that filters by company layout.** This session introduced a real regression: a guard meant to protect ONE company's edge case (Gopal Snacks' combined-page PDF layout) was scoped too broadly and silently blocked a DIFFERENT, unrelated extraction path for HUL and likely other normal companies, because the guard's own detection logic (a label must exist before it can verify anything follows it) doesn't hold for companies using a different, equally-valid disclosure convention (a bare unlabelled subtotal). **Whenever you add a guard/exception to protect against ONE observed bad case, test it against a "control" case that should NOT trigger the guard** (e.g. the same company's other fiscal year, or a totally different company) before considering it done — not just the case that motivated it.
9. **Prefer honest N/A over a silently wrong number, always.** Multiple times this session, a "clever" fallback (spatial word-position extraction, a wider text-search window) produced a plausible-looking but actually wrong number for one specific field, while working correctly for adjacent fields on the same page. When you can't achieve high confidence in an extraction for a specific case, force N/A rather than ship a guess — and say so explicitly rather than silently declaring victory.
10. **The live server (`python app.py`, uvicorn `--reload`) doesn't always reliably reload on file changes** — if a live endpoint still shows stale data after a fix + cache clear, verify with a fresh direct Python call first to isolate whether it's a reload issue or something else.
11. **Frontend "market price per share" (MPS) ratios must poll live, not fetch once.** All 13 MPS-dependent ratio cards (P/E, P/B, P/S, FCF Yield, Dividend Yield, Earnings Yield, EV/EBITDA, PEG, EV/Sales, EV/FCF, Price-to-Cash-Flow, Graham Number, Altman Z-Score) must use the shared `useLiveQuote(symbol)` hook (`frontend/src/main.jsx`), which polls `/api/quote` every 20 seconds — never a one-shot fetch inside the same `Promise.all` as the slow-changing statement data, which would freeze the price at page-load time. This is already correctly wired for all 13 as of this session; if a future MPS-based ratio card is added, make sure it follows this same pattern.
12. **Client-side derived cards (DOH, DSO, DPO, CCC, Working Capital, ROA, etc.) must share selected-year state with their parent ratio card**, not independently default to "latest". This session fixed three of these (`InventoryTurnoverGroup`, `ReceivablesTurnoverGroup`, `PayablesTurnoverGroup` wrapper components in `frontend/src/main.jsx`) — if you find another derived card independently calling its own endpoint with `to_date: null` regardless of a sibling card's year picker, it likely has the same bug.

## Architecture notes worth knowing before diving in

- **`tools/annual_report_financials.py`** is the core PDF-extraction engine — downloads a company's Annual Report from BSE/NSE, parses it with PyMuPDF, and extracts every line item every ratio needs. Most bugs live here: either (a) a label-matching regex too narrow to catch a real-world phrasing variant, (b) a page-detection heuristic false-positiving on the wrong page, or (c) a text-proximity assumption (label near its numbers) that breaks on an unusual page layout.
- **`tools/nse_xbrl.py`** wraps each `fetch_X_from_annual_report` with year-selection logic (explicit year vs. "latest" cascade) and the Supabase DB fast-path (`try_db_ratio`).
- **`tools/db_ratio_reader.py`** is the Supabase read/write layer — has a freshness guard (added this session) that rejects a cached row if a newer fiscal year now exists, but does NOT detect "this row was computed by since-fixed buggy code".
- **`tools/precompute_worker.py`** is a ONE-SHOT backfill tool, NOT a recurring cron job. It marks `(symbol, ratio_no)` pairs "done" in a `refresh_jobs` table and skips already-done pairs on future runs by default (`skip_done=True`) — it does not periodically re-check already-computed values. This means a code fix never self-heals the cache on its own; someone has to either view that company live (which writes back through `write_db_ratio`) or explicitly clear+recompute.
- **`tools/_refix_tcl_cash_ratios.py`** (added this session) is the pattern to follow for targeted cache remediation: define a small `TARGET_RATIO_NOS` set, iterate all companies, call `compute_one()` directly (bypassing the `done_set` skip logic entirely) so it always recomputes fresh. Reuse/extend this script rather than writing a new one each time; delete the specific `ratio_no`(s)' `applicable=False` rows from `ratio_values` first (with user approval), then run this script.
- Companies whose Annual Report combines the Balance Sheet and P&L onto ONE page (confirmed on Gopal Snacks specifically) need a spatial (word-position-based) extraction fallback — see `_find_row_values_spatial`, `_page_words`, `_side_by_side_split_x`. This fallback is proven reliable for some fields (Revenue, Inventory, Receivables, Total Assets, Total Current Assets, Equity) but NOT YET reliable for others (Total Current Liabilities, Cash — these are deliberately forced to N/A rather than risk a wrong number; see `_label_directly_followed_by_number` guard, scoped to `combined_page` only per lesson #8 above).
